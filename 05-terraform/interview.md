# Module 05 - Terraform: scenario-based production interview Q&A

Format: **Scenario** -> **Model answer** (diagnose / decide / fix / prevent) -> **Say to leadership** where relevant. Every answer maps to a lab.

---

### 1. Terraform plan wants to destroy and recreate the production database after a module upgrade
**Answer.** Stop, do not apply. Read the plan for `must be replaced` and the `# forces replacement` attribute. Typical causes: a resource address changed (module/resource rename), a ForceNew attribute changed (name, zone, SKU family), or a provider major upgrade changed a default. Fix: for renames add a `moved` block (Lab 02); for provider changes pin the provider and read the upgrade guide; if replacement is truly needed, do a controlled migration (restore from backup/replica, cutover) not an in-place destroy. Add `lifecycle { prevent_destroy = true }` to stateful resources and a Conftest rule that fails plans deleting DBs unless a label is present (Lab 05). **Prevent:** plan in PR, policy gate, tests for module upgrades with `moved`.
**Leadership:** "A guardrail stopped an outage; we now require an explicit approval to destroy stateful resources."

### 2. A teammate ran `terraform apply` locally and the pipeline now shows unexpected changes
**Answer.** Local apply diverged from reviewed code (or applied uncommitted changes). Check git for what is merged vs what state reflects: `terraform plan` shows the delta. Decide: if local change was wrong, apply from `main` to revert; if right, commit it via PR. Prevent: remove human write credentials to shared envs (only the CI OIDC identity can write; engineers get Reader), state-bucket RBAC, break-glass role with audit alerts. Cultural: blameless, make the paved path faster than the shortcut.

### 3. `Error acquiring the state lock` during an incident when you need to apply a fix fast
**Answer.** Read lock info (ID, who, when, operation). Check CI for a running/hung job and cancel it properly. If nothing is running (runner died), `terraform force-unlock <id>` (Lab 03). Never unlock while an apply may be live: you risk state corruption. After, verify state with `terraform plan`, restore from a bucket version if corrupt. Mitigate: `-lock-timeout`, CI concurrency groups with `cancel-in-progress: false` for applies, runner health.

### 4. State file contains secrets. Security found DB passwords in the state bucket
**Answer.** State is sensitive by nature. Short term: restrict access to the backend (RBAC, private endpoint, no shared keys), enable encryption, audit access. Medium: stop generating secrets in Terraform; use Entra/IAM auth for DBs, or generate secrets out of band (Key Vault/ESO) and reference them; use ephemeral resources/write-only attributes where the provider supports them. Rotate the exposed secrets now. Leadership: state = secret store of record, treat access like prod DB access.

### 5. You must split a 3,000-resource state that takes 25 minutes to plan
**Answer.** Cause: giant state, API throttling, serialised graph. Plan: freeze applies, back up state, split by lifecycle and blast radius (network, shared services, per-app). Use `moved` + `import` blocks or `state mv -state-out`, then `plan` both roots expecting zero changes (Lab 03). Interim speedups: `-refresh=false` for dry runs, `-parallelism`, targeted plans only as a diagnostic. Rule going forward: one state per env per component; budget of resources per state.

### 6. How do you let 50 teams create infrastructure without becoming a ticket queue?
**Answer.** Product modules (standard service, standard Postgres) with secure defaults and few inputs; teams open a PR (generated by Backstage) to `acme-infra`; CI runs fmt, validate, policy, plan; code owners = platform + owning team; auto-merge for low-risk (dev, standard SKU) with required checks; human review for prod and policy exceptions. Metrics: lead time request-to-resource, % requests fully automated, number of exceptions.

### 7. Module consumers are stuck on v1 two years after v3 shipped. What do you do?
**Answer.** Measure first (code search for `?ref=v1`, scorecard in Backstage). Understand why: breaking changes without migration path, fear, no capacity. Actions: Renovate PRs with changelog and plan output, `moved` blocks to make upgrades zero-diff, office hours, a hard deprecation date agreed with leadership, and a compat shim for the worst break. Staff move: tie the date to a risk (v1 uses a retired API / vulnerable provider), not a preference.

### 8. Choose: workspaces vs directories vs Terragrunt
**Answer.** Workspaces share code and backend credentials; easy to run in the wrong one, no per-env access control or version pinning; use them only for ephemeral copies. Directory-per-env gives separate state, access boundaries via CODEOWNERS and credentials, and promotion by bumping a module ref. Terragrunt adds DRY backend config, dependencies and `run-all` at the cost of another tool/learning curve. My default at scale: directory-per-env + Terragrunt, one state per component (Lab 04).

### 9. A provider upgrade (azurerm 3 -> 4) breaks 200 repos on Monday
**Answer.** It should never be a surprise: modules declare `~> 3.x` ranges, consumers have lock files committed, Renovate groups provider bumps. Process: upgrade the *modules* first on a branch, run `terraform test` + Terratest on examples, publish a new major with a migration guide, then roll consumers in waves (dev first), watching plan diffs. Provide a codemod for known renames. Keep N-1 supported. Rollback = pin back and restore `.terraform.lock.hcl`.

### 10. How do you stop someone from disabling a security feature (public access = true) in a module?
**Answer.** Defence in depth: secure default; `validation`/`precondition` rejecting forbidden values; Checkov/Trivy in PR; Conftest on plan JSON (Lab 05); cloud-side Azure Policy / SCP as backstop for resources created outside Terraform; exceptions via a file with owner, ticket and expiry. CODEOWNERS on policy and module dirs.

### 11. Drift: someone changed a tag/firewall rule in the portal
**Answer.** Detect with nightly `plan -detailed-exitcode` that opens an issue (Lab 06). Triage: is the portal change correct? If yes, codify via PR; if no, apply to revert. Prevent: read-only portal access for humans in prod, Azure Policy deny/modify for tag drift, alerts on activity-log writes by non-pipeline principals. Be explicit that `ignore_changes` is for fields owned by another system (autoscaler), not for hiding drift.

### 12. Terraform Cloud vs Atlantis vs GitHub Actions: recommend one
**Answer.** Criteria: scale, policy needs, RBAC/audit, cost, ops burden. Actions: no new service, native OIDC, but you build locking, plan comments, drift yourself. Atlantis: PR-native UX and per-directory locks, self-hosted ops burden and a webhook endpoint to secure. TFC/Spacelift: hosted runners, policy (Sentinel/OPA), private registry, RBAC, drift, at a per-resource price. Decision for a mid-size org with strong GitHub: Actions + OIDC + Conftest; for 500+ workspaces and compliance: Spacelift/TFC.

### 13. Import 400 manually created resources into Terraform
**Answer.** Do not import by hand. Inventory (az resource list / Azure Resource Graph), generate config with `import` blocks + `-generate-config-out` or aztfexport, review and refactor generated code into modules, then `plan` must be a no-op. Do it in slices by resource group, with owners approving. Never `apply` until the plan is clean; some attributes are not importable (secrets), plan for them.

### 13b. Same question, but the clock is ticking: a vendor mandates all infra be in IaC by quarter-end
**Answer.** Triage by risk: internet-facing and data stores first, generate code with aztfexport, accept generated-but-unrefactored code under a `legacy/` tree with owner tags, schedule refactor into modules. Report coverage % weekly. Don't boil the ocean.

### 14. `terraform plan` shows changes on every run for a resource nobody touched
**Answer.** Perpetual diff: provider normalises a value differently (case, ordering, defaults) or an external system mutates it (policy adding tags, autoscaler changing count). Diagnose with `terraform plan` output, `TF_LOG=debug` for provider read, compare state vs config. Fix by matching the normalised value, using `ignore_changes` on the specific attribute with a comment, or removing the competing writer. Open a provider issue if it is a bug.

### 15. A module author wants 60 input variables to cover every use-case
**Answer.** Push back: modules are contracts. Split into smaller primitives; keep the product module opinionated with <10 inputs; offer an escape hatch (use the primitives directly) rather than exposing every attribute. Track requests for new inputs as product feedback, add only when 3+ consumers need it.

### 16. Cost control in IaC
**Answer.** Enforce tags (cost-center), size allow-lists via validation (`contains([...], var.sku)`), Infracost in PR comments showing monthly delta, budget alerts per subscription, TTL tag + sweeper for sandbox resources, policy that blocks expensive SKUs in dev. Report showback by tag.

### 17. How would you test a module change safely before it hits 100 consumers?
**Answer.** Unit tests with mock providers every PR; Terratest integration on release candidate in sandbox subscription; canary: tag `v2.0.0-rc.1`, upgrade 2-3 friendly consumers, review plans; publish final; Renovate waves. Include a "plan is a no-op for existing consumers" test where possible (apply v1, plan v2).

### 18. Walk me through a bad apply that failed halfway in production
**Answer.** Stay calm; state records what succeeded. Do not re-run blindly. Read the error (quota, permission, dependency, API). `terraform plan` to see the remaining delta. Fix the cause, re-apply; Terraform is convergent. If a resource is half-created/tainted, inspect in cloud and decide `import`/`taint`/delete. Communicate status, avoid concurrent runs (lock), write a post-incident review: add precondition, quota check, or smaller changes.

### 19. Why not just use Crossplane for everything?
**Answer.** It excels at self-service and continuous reconcile with K8s RBAC/GitOps, but no plan review, a heavy control plane (CRDs, provider memory), provider coverage and quality vary, debugging is multi-layer, and the control cluster becomes critical infrastructure (bootstrap and DR). I use Terraform for foundations and Crossplane/pipeline-backed APIs for developer resources, never both for the same resource.

### 20. How do you prove the Terraform platform is a success?
**Answer.** Time from request to provisioned resource, % of infra under IaC, policy violations caught in PR vs production, drift incidents, module adoption by version, change failure rate for infra changes, developer satisfaction. Use these in the quarterly review and to prioritise the roadmap.

## Rapid-fire (answer in 20 seconds each)
- `moved` vs `state mv`? Declarative, reviewable, repeatable vs imperative one-off.
- `for_each` vs `count`? Stable keys vs index shifting.
- `ignore_changes` use? Fields owned by another controller, not drift hiding.
- `-target`? Diagnostic/emergency only; it skips dependency correctness.
- Sensitive values? Hidden from output, still in state.
- `terraform_remote_state` downside? Couples roots, exposes whole state; prefer outputs published deliberately/data sources.
- Lock file? Commit it, it pins provider hashes.
- Why pin `required_version`? Reproducible plans across laptops/CI.
