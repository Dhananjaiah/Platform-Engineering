# Lab 07-01 - RFC and ADR process (and a worked RFC)

## Goal
Create the repo, templates, review mechanics and automation for RFCs (proposals under debate) and ADRs (decisions made), then run a real RFC through the process: "Standardise on GitOps promotion via PRs".

## Prereqs
`gh`, `git`. A repo `acme-lab-<you>/platform-rfcs`.

## Step 1 - Repo and structure
```bash
gh repo create acme-lab-<you>/platform-rfcs --public --clone && cd platform-rfcs
mkdir -p rfcs adrs templates .github/workflows
cat > CODEOWNERS <<'EOF'
/rfcs/   @acme-lab-<you>/platform-admins
/adrs/   @acme-lab-<you>/platform-admins
EOF
```
Why separate: **RFC** = "should we?" (open for comment, time-boxed, can be rejected). **ADR** = "we decided" (short, immutable record with context; superseded rather than edited).

## Step 2 - Templates
```bash
cat > templates/rfc.md <<'EOF'
# RFC NNNN: <title>
- Author(s): 
- Status: draft | in-review | accepted | rejected | withdrawn | superseded-by RFC-XXXX
- Reviewers (required): security, SRE, <affected teams>
- Review window closes: YYYY-MM-DD (min 7 days)
- Decision owner: 

## Summary (3 sentences)
## Problem and evidence
(Data: incidents, tickets, DORA numbers, interviews. Who is hurt, how often.)
## Goals / Non-goals
## Proposal
(Design with diagrams. How it works in the golden path. Security and operability.)
## Alternatives considered
(At least two, including "do nothing", and why rejected.)
## Migration and rollout
(Phases, owners, pilot teams, rollback, deprecation dates.)
## Risks and open questions
## Success metrics
(What number moves, by when, how measured.)
## Cost
(People, infra, licences, opportunity cost.)
## Appendix
EOF
cat > templates/adr.md <<'EOF'
# ADR NNNN: <decision>
Status: proposed | accepted | superseded by ADR-XXXX | Date: YYYY-MM-DD | Deciders: 
## Context
## Decision
## Consequences (positive and negative)
## Alternatives considered
## Review trigger (what would make us revisit)
EOF
```

## Step 3 - Automation: numbering and lint
```bash
cat > .github/workflows/rfc-check.yml <<'EOF'
name: rfc-check
on:
  pull_request:
    paths: ["rfcs/**", "adrs/**"]
permissions: { contents: read }
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@SHA
      - name: Required sections present
        run: |
          for f in $(git diff --name-only origin/${{ github.base_ref }}...HEAD -- 'rfcs/*.md'); do
            for s in "## Problem and evidence" "## Alternatives considered" "## Migration and rollout" "## Success metrics"; do
              grep -q "$s" "$f" || { echo "::error file=$f::missing section: $s"; exit 1; }
            done
          done
      - name: Status header present
        run: grep -L "^- Status:" rfcs/*.md | (! grep .)
EOF
git add -A && git commit -m "feat: RFC/ADR process" && git push -u origin main
```
(`fetch-depth: 0` on checkout is required for the `git diff` step; add it.) Enforce with a ruleset: PRs to `rfcs/` need approval from CODEOWNERS plus required reviewers from security/SRE by team mention.

## Step 4 - The worked RFC (write it yourself, this is the practice)
```bash
git checkout -b rfc/0007-gitops-promotion
cp templates/rfc.md rfcs/0007-gitops-promotion-via-pr.md
```
Fill in with real content. A strong example:
- **Summary**: Promote changes between environments by pull requests to the GitOps repo that copy an image digest from the lower environment, with automated checks, instead of CI-driven `kubectl`/`helm` deploys.
- **Problem and evidence**: 38 % of services deploy via Jenkins `kubectl apply`; 11 prod incidents in 6 months traced to config drift or unreviewed hotfixes; median rollback 42 minutes; audit finding on missing change evidence.
- **Goals**: all prod changes reviewed and reproducible; rollback < 5 minutes; zero cluster credentials in CI. **Non-goals**: replacing Argo Rollouts decisions, changing teams' branching models.
- **Proposal**: CI writes digest to dev overlay (auto-merge); promotion PR to stg/prd generated by workflow, with required checks (render, policy tests, signature verification), CODEOWNERS approval for prd; ArgoCD auto-syncs; rollback = revert PR via emergency workflow.
- **Alternatives**: (A) Image Updater (less approval control), (B) Kargo (more UX, another control plane, revisit at 200 services), (C) status quo.
- **Migration**: pilot 3 teams in Q1, wave 2 (15 teams) Q2, wave 3 Q3, Jenkins deploy credentials revoked Q4; migration squad; scripts to convert.
- **Risks**: PR latency (mitigated by auto-merge for stg), config-repo scalability (mitigated by manifest paths/sharding), developer frustration (mitigated by office hours).
- **Success metrics**: lead time p50 -30 %, rollback p50 < 5 min, 0 prod deploys by humans via kubectl, CFR unchanged or lower; measured via the DORA pipeline.
- **Cost**: 2 engineers x 2 quarters, tooling ~0.

## Step 5 - Run the review (mechanics matter)
```bash
git add -A && git commit -m "rfc: 0007 gitops promotion via PR" && git push -u origin HEAD
gh pr create -t "RFC 0007: GitOps promotion via PR" -b "Review window closes in 10 days. Please comment on risks and alternatives." -r acme-lab-<you>/team-security,acme-lab-<you>/team-sre
```
Process: (1) **pre-wire**: talk 1:1 with the 3-4 people most affected *before* publishing (no surprises); (2) announce in channel with a 2-minute summary and the deadline; (3) hold one live review session for contentious points; (4) respond to every comment (accept/decline with reason), update the doc; (5) decision by the named owner at the deadline (consensus is not required; disagree-and-commit with objections recorded); (6) merge with status `accepted`; create ADR 00NN capturing the decision in short form; (7) link tracking issues/epics.
Tools: `gh pr view --comments`, `gh pr checks`, label states `rfc/in-review`, `rfc/accepted`.
```bash
gh pr view --comments | head -50
gh pr edit --add-label rfc/in-review
```

## Step 6 - Close the loop
After accepting: ADR + roadmap items + metrics dashboard; schedule a review at 6 months comparing success metrics. Maintain an index:
```bash
cat > README.md <<'EOF'
# Platform RFCs and ADRs
| # | Title | Status | Owner |
|---|---|---|---|
| RFC 0007 | GitOps promotion via PR | accepted | you |
| ADR 0004 | Portal build vs buy | accepted | you |
EOF
```
Anti-patterns: RFCs as approvals theatre (decided before publishing), RFCs nobody reads (too long: cap at ~6 pages, summary first), no decision date, endless bikeshedding (timebox, owner decides), ADRs that are edited after the fact (supersede instead).

## Break it on purpose
1. Publish an RFC with no alternatives: have a peer review it and list what you'd be asked.
2. Skip pre-wiring with security; watch (in a role-play with a colleague) a late objection derail the review: this is why you pre-wire.

## Talking points
RFC vs ADR, pre-wiring, time-boxed review with named decision owner, recorded objections, success metrics and a 6-month review, short documents with evidence.
