# Module 02 - Internal Developer Platform: scenario-based production Q&A

---

### 1. Your CTO says "build us an internal developer platform". Where do you start?
**Answer.** Not with tools. Week 1-4 discovery: developer interviews (10-15 across teams), data (CI/deploy method inventory, ticket categories, incident causes, DORA baseline), and define the problem in business terms (e.g. "12 days to first deploy, 40 % of tickets are provisioning, 4 CI systems"). Decide a thin first slice (Team Topologies TVP): service golden path + namespace + secrets + standard dashboards. Pick a pilot with 2-3 friendly teams, deliver a working vertical slice in a quarter, measure (time-to-first-deploy, adoption, satisfaction), then widen. Staff behaviours: write the ADR/RFC, get a sponsor, define success metrics, hire/shape the platform team as a product team (PM or product-minded lead). Anti-patterns to avoid: build everything first, mandate before value, platform as ticket queue.

### 2. Teams say the golden path is too restrictive and they leave it
**Answer.** Analyse reasons (deviation log): missing features (add), real edge cases (support an extension point), preference (say no). Golden path = strict on interfaces and security, flexible inside the app. Add escape hatches (extra manifests, annotations), a deviation process with expiry, and a BYO tier with a minimal contract. Make staying on the path clearly better (pre-wired observability, on-call support, automated upgrades, faster approvals). Measure deviation rate and reasons; recurring reasons become roadmap items. If 30 % want websockets, the path lacks websockets.

### 3. How do you decide what the platform provides versus what teams own?
**Answer.** Use cognitive load and leverage: platform provides capabilities that are undifferentiated, high-pain, high-reach, and security/compliance-critical (CI/CD, runtime, secrets, identity, observability plumbing, networking). Teams own domain logic, their SLOs, data models, and how they use the platform. Criteria matrix: pain x reach x cost-to-build x risk. The "thinnest viable platform": ship the minimum that removes the most load, and document the rest. Revisit regularly as capabilities commoditise.

### 4. Design self-service database provisioning with guardrails
**Answer.** A platform API with a narrow contract: `PostgresInstance { owner, size (S/M/L), storageGB, ha }`. Implementation by Crossplane composition (in-cluster operator or cloud managed service) or Terraform-via-PR. Guardrails: schema bounds, secure defaults (private networking, TLS, backups, encryption, identity auth), naming and labels, quotas per team, cost labels, approval only for prod/large via PR review, deletion protection. Credentials delivered via workload identity or ESO, not tickets/emails. Observability: provisioning SLO (p95 < 10 min), failure alerts, cost showback. Day-2: version upgrade policy, backup restore tests, a clear ownership split (platform: engine/patching, team: schema/queries).

### 5. Developers want raw Kubernetes access; the platform team wants to hide it
**Answer.** Both are wrong as absolutes. Offer layers: default path hides K8s behind a golden chart/spec; advanced users can use Kustomize/raw manifests *within* policy guardrails (Kyverno, quotas, PSS). Provide read access to cluster state (logs, events, describe) in the portal and via RBAC; write via GitOps. Measure: if most teams escape, the abstraction is wrong; if nobody does, perhaps too rigid or too good. State principle: abstraction should hide decisions the team shouldn't make, not understanding they need (people debugging at 3 am need to see Kubernetes).

### 6. How would you prove the platform is worth its cost to the CFO?
**Answer.** Baseline before and after, on metrics finance respects. Efficiency: time-to-first-deploy, lead time, ticket volume x handling time, onboarding time; convert to engineer-hours x loaded cost. Risk: incidents/MTTR, policy violations caught pre-prod, audit effort saved. Cost: cloud savings from right-sizing/autoscaling/spot, retired tools (Jenkins licences). Investment: platform headcount + tooling. Present payback period (e.g. 14 months) with ranges and assumptions, supported by developer survey results. Be explicit about what is measured vs estimated.

### 7. Two business units want conflicting platform features; platform capacity is limited
**Answer.** Prioritise using an explicit framework (impact on developer time and business outcomes x number of teams x effort x strategic fit), via a public roadmap and a platform advisory group of representatives. Seek common abstractions rather than two features; offer inner-source for the unique one with platform review; be transparent about what is not being done and why. Escalate trade-offs with data to a steering group rather than deciding politically. Document in an RFC.

### 8. A critical team refuses to migrate from their custom deploy scripts to the platform
**Answer.** Find the real objection (risk, time, missing feature, trust). Reduce their cost: migration squad pair-programs the first service, automate conversion, run in parallel until parity. Fix gaps they identify (they are valuable design partners). Create pull: features only on the path (observability, canary, auto-rollback, faster compliance). Use data: show their lead time/failure rate vs migrated teams. Use leadership only for time-bound sunset of the old system after alternatives are proven and communicated early. Never force a migration that increases their risk without a safety net.

### 9. How do you design the platform API so it can evolve without breaking users?
**Answer.** Versioned APIs (`v1alpha1 -> v1beta1 -> v1`) with conversion; additive changes by default; defaults for new fields; deprecation policy (announce, warn in CI/Backstage, auto-migration PRs, sunset date); composition/chart revisions with `Manual` update policy for prod; contract tests; changelog and migration guides; telemetry to know who uses which version; no breaking change without an RFC. Keep the surface area small, because every field is a promise.

### 10. DORA metrics show lead time is 6 days. What now?
**Answer.** Decompose: coding -> PR open -> review wait -> CI time -> merge -> deploy wait -> prod. Use data per stage (GitHub timestamps, CI durations, deploy events). Typical: review wait and manual approvals dominate. Actions: reviewer SLAs/auto-assignment, smaller PRs, CODEOWNERS tuning, faster CI (caching, test parallelism), auto-promote through stages with progressive delivery and SLO gates, remove CAB for low-risk changes with automated evidence. Validate by re-measuring; avoid gaming (don't split PRs just to reduce numbers). Present results as a trend per team versus itself.

### 11. Platform team is a bottleneck with a 3-week backlog of requests
**Answer.** Root-cause the request types: if provisioning/one-offs, automate as self-service; if questions, improve docs/office hours/Backstage troubleshooting; if bespoke features, intake process with prioritisation and inner-source. Set interaction modes: X-as-a-Service default, collaboration time-boxed. Measure ticket volume by category and aim to eliminate the top two categories by automation each quarter. Protect capacity: WIP limits, an on-support rota rotating one engineer, and a rule that recurring toil gets automated.

### 12. Security wants to enforce mandatory scans and image signing across all pipelines; developers resist
**Answer.** Embed in the golden path so it's free for teams (reusable workflow does scans/signing; no per-team work), enforce with rulesets/admission in waves (audit -> enforce), optimise speed (caching, parallelism), provide quick triage tools (dashboards, auto-created issues with fix PRs, Renovate), allow time-boxed exceptions with owners, and share metrics both ways (vulns fixed, build-time impact). Align with security on severity thresholds to avoid alert fatigue. Joint ownership: security owns policy content, platform owns delivery mechanism.

### 13. Explain the platform architecture on a whiteboard in 5 minutes
**Answer.** Draw the flow: developer -> Backstage (catalog/templates/docs) -> GitHub (repo, reusable workflows) -> Terraform/Crossplane (cloud resources via PR) -> CI (build, test, scan, SBOM, sign, push) -> GitOps repo update -> ArgoCD ApplicationSets -> AKS clusters (Kyverno admission, Rollouts) -> observability back into Backstage. Annotate each hop with the interface, owner, SLO and failure behaviour (e.g. "if Backstage is down you can still deploy via git"). Then DORA/DX measurement closing the loop into the roadmap. Offer trade-offs unprompted (hub-and-spoke, PR vs API for infra, build vs buy).

### 14. When should the platform say no?
**Answer.** When a request benefits one team and adds ongoing cost to the platform (inner-source instead), conflicts with security/compliance, duplicates an existing capability, or increases surface area without evidence of demand (<3 teams). Say no with an alternative: "we won't build X, but here is the extension point and review support" and transparent roadmap reasons. Platform health depends on a coherent, small product.

### 15. You're asked to create a "platform maturity model" for teams. How?
**Answer.** Define levels with observable, automated criteria (e.g. Level 1: catalog + CI on platform workflows; Level 2: GitOps deploy, SLOs, runbooks; Level 3: progressive delivery, scorecard gold, DR tested), implemented as scorecards evidenced by system data. Use it to guide improvement and prioritise platform investment, not to shame. Tie levels to service tiers (tier-1 requires Level 3), review quarterly, publish aggregated progress, celebrate teams. Avoid vanity checks nobody acts on.
